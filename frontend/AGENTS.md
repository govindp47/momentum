# Momentum Frontend — Agent Instructions

## Scope and intent

These instructions apply to everything under `frontend/`.

Momentum is a local-first personal tracker. The frontend is one React application with a
shared shell and multiple sub-applications, currently including Ledger and Stride. Treat the
existing product behavior, API contracts, navigation model, and visual language as established.

For frontend-only work, do not modify files outside `frontend/` unless the task explicitly
authorizes a cross-boundary change. Prefer the smallest coherent change and do not redesign,
restructure, or modernize unrelated code while solving a focused task.

## Stack and tooling

- React with TypeScript in strict mode
- TanStack Start and TanStack Router with SSR and file-based routing
- TanStack Query for server state
- Tailwind CSS v4 with theme variables in `src/styles.css`
- shadcn-style Radix UI primitives in `src/components/ui/`
- Vite and Bun
- Lucide icons, Recharts, React Hook Form, and Zod where the existing feature uses them

Use Bun for package and script operations. Do not introduce npm, pnpm, or yarn lockfiles.

## Source map

```text
src/
├── api/                 # Shared HTTP client and domain endpoint modules
├── components/
│   ├── ui/              # Low-level shared UI primitives
│   └── <feature>/       # Reusable feature/presentation components
├── hooks/
│   └── queries/         # TanStack Query hooks, keys, mutations, invalidation
├── lib/                 # Cross-cutting browser/SSR utilities, theme, telemetry
├── routes/              # TanStack Router file routes and route-local UI
├── types/               # API transport request/response types
├── routeTree.gen.ts     # Generated by TanStack Router; never edit manually
├── router.tsx           # Router and per-router QueryClient composition
├── start.ts             # TanStack Start request middleware
├── server.ts            # Custom SSR server/error boundary entry
└── styles.css           # Tailwind theme tokens and shared CSS utilities
```

Before adding a file or abstraction, inspect the relevant API module, query hooks, nearby
routes, and shared components. Reuse an existing pattern when it fits; do not create generic
layers for hypothetical future use.

## Dependency direction

Keep the normal data flow explicit:

```text
route or feature component
  -> query hook
  -> domain API module
  -> shared API client
  -> backend
```

- `src/types/` describes transport contracts. Keep API field names and enum values exactly as
  sent by the backend; do not silently camel-case, reinterpret, or enrich them with UI state.
- `src/api/` owns endpoint paths, parameter encoding, HTTP verbs, and response typing.
- `src/hooks/queries/` owns query keys, query/mutation configuration, and cache invalidation.
- Routes and components own presentation state, user interaction, and formatting.
- UI-only labels, icons, colors, and derived display models do not belong in API types.
- Components must not contain endpoint strings or call raw `fetch()` for ordinary API work.
  The telemetry persistence path is an intentional self-contained exception because telemetry
  must not recursively depend on the normal client.

Do not add a second HTTP client, global server-state store, repository layer, or frontend
business-service layer when the existing flow covers the need.

## API contracts and HTTP behavior

Use `src/api/client.ts` for JSON endpoints and extend the appropriate domain module for new
operations. The client reads `VITE_API_BASE_URL` and already handles JSON requests, `204`
responses, error normalization, and unexpected-failure telemetry.

- Preserve `ApiError` semantics: HTTP status for server responses, `0` for network failures,
  and `-1` for response parse failures.
- Treat expected 4xx validation/business errors as user-facing failures, not telemetry events.
- Encode path values with `encodeURIComponent` and build nontrivial query strings with
  `URLSearchParams`.
- Model intentional request and response changes in `src/types/`, then update the API module,
  query hooks, and every consumer together.
- Preserve distinctions such as nullable versus optional fields, date versus datetime strings,
  ratio (`0..1`) versus percentage (`0..100`), and backend enum literals.
- Do not invent fallback data that makes a failed request appear successful.

The development server proxies `/api` to the local backend. Keep environment-specific base
URLs in environment configuration rather than hard-coding hosts in application code.

## TanStack Query and state

TanStack Query is the source of truth for remote data. Local React state is appropriate for
ephemeral UI state such as open dialogs, form drafts, filters, and optimistic interaction
details that are not authoritative server data.

- Define stable key factories in the relevant query-hook module.
- Include every input that changes a response in its query key.
- Use `enabled` for queries whose identifiers are not yet valid.
- After a mutation, invalidate all affected detail, list, aggregate, dashboard, calendar, and
  achievement queries—not just the component that initiated it.
- Use targeted invalidation where possible. Broad invalidation is acceptable only when all data
  under that prefix can genuinely be stale.
- Preserve intentional `staleTime`, sequential request behavior, disabled/manual queries, and
  other non-default settings unless the task requires changing them.
- Keep loading, empty, error, success, mutation-pending, and retry states explicit in the UI.
- Do not mirror query results into context or another global store.

When adding cross-domain dashboard data, keep the dashboard client, types, query hook, and
presentation separate from Ledger- or Stride-specific modules.

## Dates, numbers, and display semantics

Date-only API values are plain local calendar strings in `YYYY-MM-DD` format. Do not construct
them with `new Date("YYYY-MM-DD")` or derive them with `toISOString()`, because UTC conversion
can shift the visible day. Reuse the feature's existing local-date helpers.

- Keep ISO date/datetime strings as transport values until formatting at the presentation edge.
- Check the relevant type documentation before formatting numeric progress. Some fields are
  ratios and others are already percentages.
- Preserve units and duration semantics from the contract; do not guess conversions.
- Make locale-sensitive presentation explicit and keep persisted/API values locale-independent.

## Routing, navigation, and SSR

TanStack Start uses file-based routes under `src/routes/`. Read `src/routes/README.md` and inspect
nearby routes before creating or moving one.

- Define routes with `createFileRoute` and follow TanStack filename conventions for index,
  dynamic, optional, splat, and layout routes.
- `src/routes/__root.tsx` is the only root document/layout. Preserve its head content, scripts,
  query provider, global error handling, route tracking, and `<Outlet />` responsibilities.
- `src/routeTree.gen.ts` is generated. Never hand-edit, format, lint-fix, or deliberately commit
  manual changes to it; let the TanStack tooling regenerate it.
- Use TanStack `Link`, route params, search state, and navigation APIs for internal navigation.
- Add or remove navigation entries through the shared `AppShell` model. The main sidebar is for
  sub-applications; page-level destinations belong in the active sub-application navigation.
- Keep route metadata meaningful when adding user-facing pages.
- Preserve route URLs and redirect behavior unless a route-contract change is explicitly asked
  for.

Modules can execute during SSR. Do not access `window`, `document`, `navigator`, `localStorage`,
or other browser-only APIs at module scope or during unguarded server rendering. Use an effect,
an event handler, or an explicit runtime guard. Do not apply generic Next.js/Remix/Vite advice
to TanStack Start without checking the current bootstrap and server entries. Preserve CSRF and
SSR error middleware when touching application startup.

## Components and forms

- Search `src/components/ui/`, shared feature components, and neighboring routes before building
  a new component.
- Prefer composition of existing primitives over copying their markup or introducing another
  component system.
- Keep route-only components local until reuse is real. Extract components when doing so makes
  a large route clearer or provides concrete reuse.
- Keep component props narrow, explicit, and typed. Prefer `unknown` at unsafe runtime
  boundaries; avoid `any`, unsafe casts, and `@ts-ignore`.
- Follow existing form patterns. Validate at the UI boundary for fast feedback while preserving
  backend validation and displaying `ApiError` messages appropriately.
- Prevent duplicate submissions and expose pending/destructive states clearly.
- Preserve semantic HTML, labels, focus behavior, keyboard access, dialog semantics, and usable
  tap targets. Icon-only controls require an accessible name.

## Visual language and theming

Do not redesign working pages unless explicitly requested. Match the surrounding feature before
inventing a new layout.

The established language is compact, personal, responsive, and content-first:

- centered content, commonly `mx-auto w-full max-w-5xl`
- compact spacing and typography
- `rounded-xl`, `border-border/70`, `bg-card/80`, `shadow-sm`, and subtle blur/translucency
- restrained progress and activity visuals
- semantic, vibrant icon accents
- polished skeleton, loading, empty, error, disabled, and hover/focus states

Use semantic theme utilities (`bg-background`, `text-foreground`, `text-muted-foreground`,
`border-border`, `bg-card`, `bg-primary`, and status tokens) instead of hard-coded neutral
colors. All changes must remain legible in both light and dark themes. Reuse shared utilities in
`src/styles.css` and `cn()` from `src/lib/utils.ts` for conditional class merging.

Common accent intent:

- emerald/green: progress and completion
- sky/blue: information, calendar, and activity
- orange: streaks and energy
- violet: journeys and milestones
- amber: achievements and attention
- red/destructive: dangerous or failed actions

Avoid oversized generic SaaS layouts, gratuitous gradients, excessive animation, new visual
systems, or feature-specific colors that bypass the theme. If adding a reusable theme token,
define its light and dark values and register it through the Tailwind theme mapping in
`src/styles.css`.

## Errors and telemetry

Preserve existing user-facing error states and retry paths. Telemetry is developer diagnostics,
not analytics, and it must always be asynchronous, bounded, sanitized, and best-effort.

Unexpected failures worth capturing include React render failures, uncaught runtime errors,
unhandled rejections, network/parse/5xx API failures, and explicit impossible application states.
Do not report normal validation, conflict, not-found, or other expected user-correctable 4xx
responses as bugs.

Never record or attach:

- credentials, tokens, API keys, cookies, or authorization headers
- request bodies or arbitrary server/application state
- localStorage/sessionStorage contents
- sensitive query parameters or unsanitized URLs
- unbounded objects, messages, stacks, or metadata

Use the existing telemetry logger, normalizer, sanitizer, fingerprints, global handlers, and
React reporting path. Do not scatter ad-hoc telemetry calls across every component, intercept
all console output, add analytics, or add an external monitoring provider. A telemetry failure
must never cause another application failure or change the user's visible error flow.

## Generated files, dependencies, and configuration

- Do not manually edit `src/routeTree.gen.ts` or build output such as `dist/`, `.output/`, and
  `.vinxi/`.
- Do not commit `node_modules/`, generated output, secrets, or real environment files.
- Use the `@/*` import alias for cross-directory source imports; use short relative imports for
  tightly related files when that is clearer.
- Add dependencies only when the platform and existing packages cannot solve the problem
  cleanly. Explain the need and update `package.json` and `bun.lock` together.
- Preserve the Bun supply-chain guard and the existing lint, TypeScript, Prettier, Vite, and
  shadcn configuration unless the task specifically targets configuration.
- `bun run format` rewrites the tree. Use it only when broad formatting is intended; otherwise
  format or edit the touched files narrowly and review the resulting diff.

## Working method

Before editing:

1. Identify the exact feature and behavioral contract in scope.
2. Read the route/component, its query hooks, API module, transport types, and relevant shared
   components.
3. Trace callers before changing shared code.
4. Check SSR/browser boundaries and all affected query invalidations.
5. Choose the smallest implementation that follows existing patterns.

After editing:

1. Review every changed file and remove debug code, stale imports, and accidental generated
   changes.
2. Exercise the affected success, loading, empty, error, retry, and mutation states as relevant.
3. For UI work, check narrow and wide layouts, light and dark themes, and keyboard/focus behavior.
4. Run targeted checks first, then broader checks in proportion to the change.
5. Confirm that only intended frontend files changed.

Run validation from `frontend/`:

```bash
bunx tsc --noEmit
bun run lint
bun run build
```

Run all three for shared infrastructure, routing, API-contract, dependency, or production-facing
changes. For a very small documentation-only change, direct inspection is sufficient. There is
currently no dedicated frontend test script; if one is added later, run the relevant tests and
keep this guidance aligned with the actual package scripts.
